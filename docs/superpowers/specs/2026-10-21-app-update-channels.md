# Android 应用更新渠道

## 用户要求与入口

Android 宿主在“设置与平台管理 → 应用更新”中提供正式版和预览版检测。2026-10-23 起，App 包配置中的 `X.Y.Z` 是正式与开发预览版本号的唯一来源。开发预览每次运行使用 `vX.Y.Z-dev.<run_number>` 独立 Tag；正式版使用 `vX.Y.Z`。历史 `nightly` 发布继续兼容读取，但新工作流不再移动该 Tag。预览版检测同时接受开发预览、其他带版本号的测试版和后续正式版。

本功能属于宿主设置，不增加主导航，不影响设备插件更新策略。它使用项目公开发布源，不依赖已登录 Gateway，不读取、发送或变更账号、配对、聊天和插件授权资料。架构边界依照模块化插件总规格及 ADR 0042。

## 渠道行为

| 检测渠道 | 候选发布 | 默认使用场景 |
| --- | --- | --- |
| 正式版 | 已发布、非草稿、非测试标记的版本号发布 | 正式构建首次打开 |
| 预览版 | `vX.Y.Z-dev.N` 开发预览版、历史 `nightly`、其他版本号测试版以及后续正式版 | 开发或测试构建首次打开 |

预览渠道纳入后续正式版，确保测试用户能从 Beta、RC 过渡到正式版。正式渠道不把开发测试包或版本号测试包当成正式版。渠道选择是独立的本机普通偏好，保存失败会明确提示。

打开更新页面自动检测；用户也可手动重查。检查期间禁用重复检查按钮，仍允许切换渠道。切换后旧请求的结果不能覆盖当前渠道。页面使用导航返回栈拥有的 ViewModel 管理任务；离开后取消页面任务，不引入常驻后台轮询。

## 发布源与版本信息

唯一发布源是项目 `1rua/open-android-intelligence` 的 GitHub Releases。正式版通过 GitHub latest-release 接口读取；预览检查最多读取前五页，分别保留最近开发预览、带版本号测试版和历史 nightly 候选，不继续扫描全部历史页面。公开资源无需 App 保存 GitHub 凭证，依据 [GitHub Releases 接口说明](https://docs.github.com/en/rest/releases/releases)。

每个可检测发布须包含真实 APK 与 `oai-update.json`。清单字段为：

| 字段 | 含义 |
| --- | --- |
| `schemaVersion` | 清单格式版本，当前为 1 |
| `versionName` / `versionCode` | APK 内实际版本名与 Android 版本码 |
| `commit` | 构建对应的完整 Git 提交标识 |
| `channel` | `development`、`preview` 或 `stable` |
| `assetName` | 同次发布中 APK 资源名称 |
| `applicationId` / `distribution` | Android 包名与 Full/Play 分发渠道 |
| `signingCertificateSha256` | 实际 APK 签名证书的 SHA-256 指纹 |

构建与发布清单必须一致，发布前从 APK 输出信息与真实签名核验。版本号提取脚本支持 Node/RN/Electron `package.json`、Flutter `pubspec.yaml`、Android Gradle `versionName`、iOS `Info.plist` 和 Rust/Tauri `Cargo.toml`。Flutter 常见的 `X.Y.Z+build` 会提取为 `X.Y.Z`。当前 Android App 的包配置是 `apps/android/app/version.properties`，Gradle 从此文件读取 `versionName`。工作流通过 `--platform android` 明确选择该配置，不会被仓库根目录的协议包 `package.json` 覆盖；其他项目可继续使用自动识别。工作流从包配置提取严格的 `X.Y.Z` 并生成 Tag，不解析 Git Tag 来确定或进位包版本。开发预览 APK 的 `versionName` 为 `<包版本>-dev.<run_number>`，正式 APK 使用 `<包版本>`。

开发与预览版本码取构建目标提交的完整历史数；正式版本码取当前 main、合并 PR 来源提交和保留的 dev 分支三者中最大的历史数。工作流显式获取 PR head 引用，因此 fork PR 或删除来源分支不会让提交对象缺失。最大历史数再乘以 10 并加渠道阶段（开发 0、开发预览 1、正式 2），所以 squash 合并也不会让正式版码低于已发布的预览版。为保持后续版本码单调，仓库必须保留 `dev` 分支，且正式与预览发布使用同一并发组串行执行。同一提交重跑不会产生更高安装版本码；开发预览运行编号只保证 Tag 和 Release 独立，不会让同一源码的重复构建成为 App 更新候选。

更新候选必须匹配本机包名及分发渠道，并具有真实已上传的 APK 资源。以 Android 版本码决定是否可升级，不能按滚动标签名称或 GitHub 初次发布时间判断新旧，也不能提示用户安装更低版本码的 APK。Play 构建应通过原安装来源更新，不向它推荐 Full APK。

## 结果、下载与边界

页面区分正在检查、发现新版本、暂无可升级版本、尚未发布、元信息缺失以及检查失败。网络失败、限流、服务失败或最近渠道候选的清单校验失败不能显示为“已是最新版本”。更早历史 Release 缺失元数据不会阻止验证当前渠道最近发布；发布页仍可从“查看所有发布”入口打开。

发现新版本后展示版本名、渠道、发布名称与说明摘要。用户明确点击后通过系统浏览器打开对应发布页，在发布页选择安装包。本次不引入自动下载或自动安装权限。签名一致才视为已核对可覆盖；签名不同或未知时明确说明覆盖安装兼容性尚未确认，不引导卸载或清除原应用数据。

网络独立使用系统 HTTPS 证书校验，限定官方 API、本仓库发布路径及 GitHub 下载重定向来源，限制响应大小和等待时间。UI 只呈现安全、可操作的错误类型，不输出原始响应或异常中的敏感内容。

## 验收

自动化覆盖：正式/预览过滤、带编号的开发预览、历史 nightly、未来版本号测试包、同版本与更旧版本、固定上限的 Release 查询、发布和 APK 缺失、损坏清单、网络与限流失败、签名差异、分发渠道、渠道保存、请求取消、重复点击及真实设置页面文案与按钮行为。发布工作流另行覆盖多平台包版本提取、PR 正文来源、正式 Tag 强制更新和分支触发守卫。

本地执行本次改动所需的最小测试后，中文提交并推送 `main`；独立子 Agent 审查此次提交，再由完整 CI 和 APK 发布流程复核。真机由用户验证：打开设置入口、切换并重启验证渠道记忆、断网重查、打开对应发布页，以及同签名新版覆盖后的账号和本地记录保留。
