## 用户确认的完整任务

## 一、任务背景与目标

项目仓库：https://github.com/1rua/open-android-intelligence

目标分支："dev"

当前 OAI Android App 在连接不同 OAI Core 时，设备能力授权及状态显示不一致。部分 Core 连接下，通话记录、通知、短信等能力显示已授权或可用；切换 Core 后，相同客户端却可能出现未授权、需要迁移授权或无法使用等状态。

这与新的架构需求不一致。

最终目标：将所有设备能力授权统一迁移至 Android App 本地，使权限策略与 Core、账号、Agent 解耦。Core 只负责统一接入、身份与连接安全校验、能力发现、请求路由和可靠传输，不再拥有设备能力授权决定权。

本任务不是简单修改 UI 文案，而是需要检查并修复完整授权链路：

Android App → OAI Core → CLI/MCP → Agent

要求完成代码实现、历史状态迁移、文档更新、自动化测试与真实 Android 设备验收。

完成后创建指向 "dev" 的 PR，停留在 Review 阶段，不直接合并。

## 二、架构边界

### 2.1 Android App

Android 客户端负责：

- Android 系统权限申请、状态查询及撤销检测。
- 设备插件安装、启用与禁用。
- 每项设备能力的独立授权策略。
- 本地权限状态持久化。
- 敏感操作确认及临时授权管理。
- 短信、通知的被动读取与主动推送配置。
- 主动推送 Agent 接收端点白名单。
- 本地加密队列、离线恢复、投递确认。
- 设备执行、资源互斥和最终权限裁决。
- 授权日志及用户紧急停止操作。

权限数据属于客户端安装实例，不再按 Core 地址、Core 账号或 Agent 分别保存。

### 2.2 OAI Core

Core 只负责：

- CLI / REST API / MCP 统一能力调用入口。
- 已连接设备发现及能力发现。
- 连接认证、设备配对、传输凭据及请求合法性校验。
- 设备请求路由、协议和 Schema 校验。
- 请求状态、取消、超时、幂等和可靠结果交付。
- Agent 主动推送接收端点注册、发现和路由。

Core 不得：

- 维护第二套设备能力授权开关。
- 使用旧账号授权数据否决 Android 已允许的设备能力。
- 替 Android 批准、撤销或扩展权限。
- 根据 Agent 自报名称或操作原因授予额外权限。
- 将 Agent Gateway 插件 setup 作为设备授权前置条件。

注意：取消 Core 的能力授权职能，不等于取消连接认证和设备访问安全。

不需要建立 Agent 独立身份认证体系，但仍必须验证调用入口的合法访问凭据与目标设备绑定关系。跨账号调用不得被旧账号级能力授权拦截，也不得由此开放匿名设备访问。

### 2.3 Agent

所有 Agent，包括 Hermes、DSH、Codex 和其他支持 CLI/MCP 的 Agent，统一通过 OAI Core 接入。

不要求独立注册 Agent 身份。

每次设备能力请求必须声明：

- Agent 名称。
- 操作目的。
- 目标设备及能力。
- 具体操作参数。

Agent 名称和操作目的仅作为展示和审计信息，不属于可信身份凭据。

任意合法接入的 Agent 可以向已建立合法设备访问关系的客户端提交请求，最终是否执行由 App 决定。

不得将设备访问机制与原生会话账号隔离混为一谈，也不得因此开放其他账号的私有会话、附件或历史数据。

## 三、历史授权彻底清理

废弃旧版本中按 Core、账号、配对分别存储设备能力授权的机制。

重点检查：

- "PairingGrantState"
- "PairingGrantPersistence"
- "CapabilityPublisher"
- "DeviceCapabilitySyncState"
- "PluginManagementScreen"
- Platform Kernel 授权链路
- Core 历史设备能力 grant / enabled 状态
- 本地授权迁移与旧版兼容逻辑

以上仅为已知调查入口，应继续搜索真实数据流与依赖关系，不得只修改文件名称对应的表面逻辑。

要求：

1. 清理旧账号级、配对级设备能力授权及其不再需要的迁移标记。
2. 废弃旧授权判断，改为客户端安装实例级的全局策略。
3. 不因为 Core 切换、账号切换、断网或客户端重启改变权限。
4. 不清除 Android 系统已经授予的权限。
5. 不删除登录凭据、账号资料、设备密钥、会话、附件、插件安装记录等无关数据。
6. 清理旧授权时，未完成的敏感请求不得凭借旧许可继续执行。
7. 迁移必须幂等、可重复启动、可恢复，避免半迁移状态。
8. 不再因为旧授权迁移状态出现无法使用插件的死循环。

清理旧授权后，所有新能力默认采用「每次手动」模式，主动推送默认关闭。

## 四、客户端三级授权模型

每项设备能力具有独立总开关和独立授权模式。

模式| 行为
每次手动| Agent 请求后等待客户端用户确认
允许只读| 已授权的数据读取自动执行；写入、发送、删除及控制操作仍需确认
自动允许| 在本地授权范围和 Android 系统限制内自动执行允许的操作

### 4.1 每次手动

收到请求时展示系统通知和 App 内授权确认卡片。

展示内容至少包含：

- Agent 声明的名称。
- 操作原因。
- 请求能力。
- 操作范围及关键参数。
- 可能涉及的敏感数据或设备动作。

用户可选择：

- 拒绝
- 仅允许本次
- 允许 5 分钟
- 允许 30 分钟
- 允许 1 小时

请求最多等待 5 分钟，超时自动拒绝并返回明确错误。

临时授权在相同客户端设备、能力、操作类型和数据范围内对所有合法接入 Agent 全局共享，不按 Core、账号或 Agent 隔离。

临时授权不得扩大已批准的能力及数据范围。

用户可以随时撤销。到期、撤销、请求取消或参数发生越权变化后必须拒绝执行。

Android 强制要求的单次系统授权仍然独立生效。

### 4.2 允许只读

只读操作自动执行。

例如：

- 读取短信。
- 查询通话记录。
- 读取通知。
- 获取屏幕只读信息或已获系统许可的截图。

涉及发送、删除、点击、输入、控制等修改性操作，仍需客户端确认。

纯读取能力在「允许只读」与「自动允许」之间可能没有实际执行差异，应保持界面语义明确，不制造虚假的额外权限。

### 4.3 自动允许

在客户端本地允许的范围内自动执行操作，无需 OAI 自己重复弹窗。

但是不能绕过：

- Android Runtime Permission。
- Notification Listener 特殊访问权限。
- Accessibility Service 启用限制。
- MediaProjection 屏幕捕获同意机制。
- Android 对短信、通话记录等敏感能力的限制。
- 仍需系统确认或当前架构安全约束要求确认的操作。

三种模式均由客户端本地持久化和裁决。

## 五、短信与通知的数据访问

短信和通知分别具备：

1. 被动查询。
2. 主动推送。

两种方式的数据范围独立配置。

### 5.1 被动查询

Agent 通过 CLI/MCP 发起读取请求。

客户端按三级授权模式、系统权限和被动查询的数据范围判断是否执行。

可配置数据范围应遵循现有实际能力实现，例如应用来源、发送方、时间段、字段和内容范围。未实现的过滤条件不得伪装成可用。

### 5.2 主动推送

主动推送具有独立授权机制。

用户需要明确开启主动推送，指定数据范围，并选择接收的 Agent 端点。

主动推送不受被动读取的「每次手动」模式限制。

只要用户明确开启主动推送并完成配置，客户端就可以在所选范围内自动发送事件，不需要每条弹窗确认。

默认推送授权范围内的完整可读取内容：

- 短信：发送方、时间、正文等。
- 通知：应用来源、标题、正文、时间等。

不得补造 Android 没有提供的数据。

### 5.3 接收端点白名单

客户端从已配置、已连接的 Core 中获取注册的 Agent 接收端点。

用户可跨 Core、跨账号多选接收目标。

白名单必须绑定可验证的稳定路由端点标识，而不是 Agent 自己填写的名称。

临时 CLI/MCP Agent 可以注册接收端点，但未被 App 用户选中前不能订阅敏感数据。

Core 负责端点路由，不负责决定哪些端点具有数据接收许可。

用户移除端点后立即停止向该端点投递。

## 六、本地加密队列与离线恢复

主动推送采用客户端本地加密持久化队列。

核心要求：

- 默认保留 72 小时。
- 用户可调整为 1 小时至 7 天。
- 设置合理的容量上限及溢出清理策略。
- 每个接收端点分别记录投递状态。
- 使用稳定事件 ID 去重。
- 支持失败重试与断线恢复。
- 接收端确认 ACK 后标记投递完成。
- 未确认成功不得静默丢弃，过期和容量清理除外。
- 用户撤销推送授权或移除接收端点后，立即停止相应投递并删除不再允许保留的待发送数据。
- 恢复时重新验证授权、目标端点和连接状态。

Core 不应长期持有原始短信或通知内容，尽量仅保存可靠投递必需的最小状态。

避免客户端与 Core 双方分别实现长期敏感数据队列。

不得出现断线恢复后重复推送、发送至错误 Agent 或将旧事件错误归入其他账号的情况。

## 七、后台运行与登录生命周期

使用 Android 原生系统事件监听、后台任务调度、本地队列及按需重连实现智能后台运行。

不强制永久保持 WS/SSE 长连接。

仅在系统允许且确实需要时使用前台服务。

区分以下情况：

- App 前台运行。
- App 普通后台运行。
- 手机息屏。
- Doze 或系统限制后台网络。
- 网络断开与恢复。
- App 进程被系统回收。
- 用户主动强行停止 App。

不得承诺 Android 系统强行停止后仍可自动运行。

登录状态规则

设备授权配置与账号登录状态分离。

退出全部账号后：

- 保留本地权限设置和 Android 系统权限。
- 暂停设备能力采集和执行。
- 暂停主动推送。
- 保留尚未过期的本地加密队列并继续按有效期规则清理。
- 停止远程能力请求处理。

重新登录后恢复用户此前启用的能力，并在验证接收端点及连接关系后补发有效队列事件。

仅切换 Core 或账号、但仍保持有效登录状态时，不得重置全局权限。

## 八、屏幕读取和控制

屏幕读取与屏幕控制是两个独立能力，各自支持三级授权。

屏幕读取包括截图、屏幕内容获取等实际已实现能力。

屏幕控制包括点击、滑动、输入文字、切换应用等实际已实现操作。

分别管理权限及可用性，不得把截图许可自动扩大为屏幕控制许可。

并发控制

仅实现必要的基础保护，不开发复杂多 Agent 调度系统。

- 屏幕控制采用独占锁。
- 初始租约 30 秒。
- 允许心跳续期。
- 单次租约累计最长 5 分钟。
- 操作完成、取消或连接超时后释放。
- 冲突请求采用 FIFO 队列。
- 独立只读能力允许并发。
- 用户拥有紧急停止权限。

过期请求不得继续操作屏幕。

排队请求执行前必须重新核实权限、租约及必要的屏幕状态前置条件。

不要增加复杂优先级、可配置排队时长或大规模调度 UI。

---

## 九、统一 CLI/MCP 契约

保留统一 "oai" CLI、Core API 和 MCP 设备访问方式。

不硬编码 Hermes、DSH 或 Codex 的专属授权逻辑。

设备请求需要带有 Agent 声明名称及原因，但实际调用者合法性、设备定位及请求完整性必须由可信调用上下文保证。

请检查现有 CLI/MCP 工具、Core 设备调用契约和端点注册机制，在现有协议基础上最小化扩展。

所有能力应共享统一的请求生命周期：

提交 → 本地授权判断 → 等待确认或执行 → 返回结果 → ACK / 结束

不得让旧 Core grant、Gateway setup、配对级能力开关成为第二个权限决定点。

应明确区分：

- 本地权限拒绝。
- Android 系统权限缺失。
- 能力未安装或未实现。
- 设备离线。
- 请求等待用户确认。
- 用户拒绝。
- 请求超时。
- 版本或协议不兼容。
- 连接认证或请求绑定失败。

Core 不得把本地拒绝伪装成网络故障，也不能在未收到 Android 确认时推断操作成功。

## 十、测试与验收：强制使用 Terra 子 Agent

主 Agent 必须将 Android 客户端权限验证工作交给使用 "terra" 模型的子 Agent。

Terra 负责 Android CLI/ADB 驱动的真实运行测试，而不是只阅读源码或运行 Mock。

如果当前执行环境不能调用 Terra、没有 Android 设备或缺少测试权限，必须明确记录阻塞项，不得宣称已经完成真实设备验收。

### 10.1 环境检查

先确认：

- Android SDK / ADB 可用。
- 至少一台授权测试的 Android 设备或模拟器可连接。
- App 可以安装、启动及调试。
- CLI/MCP 能连接测试 Core。
- 测试数据、系统权限及相关服务状态可观测。

优先验证实际连接的设备，记录 Android 版本、App 版本、Core 版本和测试环境。

### 10.2 权限验证矩阵

Terra 必须覆盖：

测试项目| 必须验证的内容
通话记录| 系统读取权限、三级授权、允许与拒绝
短信| 被动查询、读取范围、主动推送、系统权限
通知| Notification Listener、应用范围、正文读取与推送
屏幕读取| 截图、MediaProjection 系统授权及权限撤销
屏幕控制| Accessibility、点击与滑动、只读禁止控制
授权切换| 每次手动、允许只读、自动允许
临时授权| 单次、5/30/60 分钟及失效处理
Core 切换| 相同客户端全局权限不变化
跨账号访问| 合法设备访问请求不受旧账号级能力 grant 限制
多 Agent| 共享临时授权、主动推送白名单
离线队列| 断网、补发、去重、ACK、过期、撤销
生命周期| 后台、息屏、进程回收、全部退出登录、重新登录

测试数据应使用专门准备的样本，避免采集或输出真实个人隐私。

Android CLI/ADB 至少应覆盖 UI 状态检查、权限状态读取、系统事件与 logcat、应用生命周期操作以及必要的自动化 UI 交互。

同时使用 OAI CLI/MCP 发起真实能力调用，验证完整链路。

ADB 测试特权不得被当作普通 Agent 拥有的权限。

对于 Android 系统要求用户在设备上手动批准的特殊权限，应验证真实系统交互，不得通过测试绕过手段冒充用户授权。

如果模拟器没有通话记录、真实 SMS 或屏幕控制所需能力，应使用合规的测试数据或记录真实阻塞，不能用假数据代替真实设备验收结论。

### 10.3 关键回归场景

重点复现原始问题：

1. 使用相同 App 连接 Core A。
2. 查看通话记录、通知和短信能力状态。
3. 切换至 Core B。
4. 确认客户端授权模式和总开关保持一致。
5. 在 Core B 下通过 CLI/MCP 发起设备请求。
6. 验证 Android 本地权限决定是否执行。
7. 断开 Core，确认本地配置仍可查看和管理。
8. 恢复连接，确认无旧 grant 拦截或错误迁移提示。

还应测试：

- 旧授权清理后首次启动默认「每次手动」。
- 主动推送默认关闭。
- 被动查询需要手动确认时，独立授权的主动推送仍正常工作。
- 未在白名单中的端点不能接收数据。
- 本地撤销在请求执行前及敏感结果交付前均生效。
- 网络重试不能导致操作重复执行。
- 正常权限拒绝不能被自动重试绕过。
- 重启后临时授权不得因时钟或状态恢复错误而延长。

### 10.4 测试证据

Terra 必须提交可复核证据：

- 实际执行命令。
- 设备和版本信息。
- 测试步骤与结果。
- 脱敏截图。
- 关键 logcat 及 Core 请求日志。
- 测试失败的原因和复现步骤。
- PASS / FAIL / BLOCKED 状态。
- 未通过项目的修复及复测记录。

不得使用「单测通过」代替 Android 真实运行验证。

## 十二、执行流程与交付要求

按以下顺序实施：

阶段一：只读审计

检查当前 "dev"，输出旧授权机制、状态来源、权限判断链路、协议依赖与文档冲突。

阶段二：制定最小可行修改方案

区分必须修改的客户端、Core、CLI/MCP 和协议部分；避免无关架构重构。

阶段三：分模块实施

优先实现全局授权与旧数据清理，再实现三级策略、主动推送和离线队列，最后处理必要的屏幕并发保护。

阶段四：测试

运行受影响的单元测试、集成测试及协议测试，并交由 Terra 子 Agent 使用 Android CLI/ADB 进行真实验证。

阶段五：文档与验收

修订需求规格、ADR、开发指南和操作文档，核对代码与文档一致性。

阶段六：提交 PR

向 "dev" 提交 PR，停留在 Review 阶段，不自动合并。

最终输出

提供：

- 修改前根因及证据。
- 最终架构与权限数据流。
- 主要修改文件及原因。
- 历史授权清理和兼容策略。
- CLI/MCP 契约变更。
- Terra 子 Agent 的真实测试报告及证据路径。
- 未解决的 Android 系统限制。
- 文档变更清单。
- PR 链接及剩余风险。

验收底线

最终应满足：

同一 Android 客户端在切换不同 OAI Core、账号或 Agent 时，其本地权限策略保持一致；Core 不再拥有设备能力授权权威；任何合法 CLI/MCP Agent 可以提出请求；所有敏感操作由 App 的本地规则裁决；主动推送只按照用户独立配置的范围与接收端点发送。

不要以隐藏错误提示、硬编码 READY、绕过本地权限检查或修改 Mock 返回值的方式宣称修复成功。

优先保证现有会话、登录、附件及通信功能不发生回归。避免过度设计非核心的多 Agent 调度能力。
