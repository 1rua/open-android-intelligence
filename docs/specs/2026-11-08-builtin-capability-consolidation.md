# 内建设备能力与「设备能力与授权」页面重构

日期：2026-11-08。状态：已确认需求，待实现。
适用基线：`dev@a688dd63`。
关联：[ADR-0059](../../adr/0059-android-is-the-sole-device-capability-authority.md)、
[全局设备授权规格](2026-11-01-global-device-authorization.md)、
[Android 设置系统](../../architecture/2026-11-05-android-settings-system.zh-CN.md)、
[设置信息架构](2026-10-24-settings-information-architecture.md)。

本规格取代此前“随 APK 打包内置插件包、由用户在插件管理里手动安装并启用”的装配方式，
以及授权子页上“临时授权”“短信与通知主动推送”“技术说明”三类入口的组织方式。
本规格不改变设备能力授权链路的权威归属：Android 安装实例仍是唯一权威。

## 一、问题

当前「设置 → 设备能力与授权」把五类不同性质的信息压在同一屏：能力入口、插件 ID 与技术说明、
临时授权列表、独立主动推送入口、底部技术备注。用户看到的是「未启用 · org.openandroidintelligence.sms」
这样的行，既判断不了能力能不能用，也不知道该点哪里才能恢复。

更要紧的是三处结构性错误：

1. **官方能力被当成第三方插件管理。** 六个官方能力以签名的 `.alp` 包随 APK 打包，但必须由用户
   逐个点击「安装」再点「启用」，装完仍然是停用状态；界面上还有与第三方插件相同的「卸载」按钮。
   用户被迫管理工作技能本不该感知的实现细节。
2. **屏幕截图的系统权限引导指向错误的系统页面。** 底层早已是“无障碍优先、MediaProjection 仅作
   显式备用”，但授权需求映射把 `kernel.screen.capture` 无条件映射为投屏授权，截图详情页因此
   只有「请求屏幕捕获系统许可」一个入口，没有任何无障碍服务入口。用户在无障碍截图本来可用的
   情况下被引导去授权屏幕共享。
3. **状态判定分散且互相矛盾。** 「安装态」短路在「本机授权」之前，同一能力可能出现“已就绪”
   的权限行与“需授权”的能力行并存；Core 断连被表述成插件缺失；`已开启` 与 `已就绪` 没有统一
   判定规则。

## 二、目标

用户安装 OAI App 后，六项官方能力就像 App 自带功能一样存在：无需安装、无需启用、无需在插件
管理里看见它们。用户只在「设备能力与授权」中决定是否开启、是否授权，以及查看真实状态。

主页面只剩三组六项能力加一个插件管理入口；每项能力的完整配置（开关、本机授权策略、Android
系统权限及正确设置入口、实际可用状态、该能力专属设置）都收进对应详情页。

## 三、主页面信息架构

| 分组 | 条目 | 详情负责的内容 |
| --- | --- | --- |
| 屏幕 | 屏幕内容读取 | 开关与授权模式、无障碍服务、运行状态、Core 同步、停止屏幕请求 |
| 屏幕 | 屏幕截图 | 开关与授权模式、截图来源与系统权限入口、运行状态、Core 同步 |
| 屏幕 | 屏幕控制 | 开关与授权模式、无障碍服务、运行状态、Core 同步、停止屏幕请求 |
| 通讯与通知 | 短信 | 短信读取主开关 + 三项子能力开关、被动范围、短信权限、短信主动推送与推送目标 |
| 通讯与通知 | 通知读取 | 开关与授权模式、通知使用权、采集范围与投递、通知主动推送与推送目标 |
| 通讯与通知 | 通话记录 | 开关与授权模式、通话记录权限、运行状态、Core 同步 |
| 更多 | 插件管理 | 第三方插件的安装、启用、停用、卸载与能力快捷入口 |

每行只显示：名称、一个简洁状态、进入详情的箭头。不显示插件 ID、提供者标识、能力 ID、
参数摘要、技术备注。

### 状态词与判定规则

主页面只用四个状态词：**已开启 / 已关闭 / 需授权 / 不可用**。判定按固定顺序进行，命中即停：

1. `不可用`：内建能力加载失败、能力未在已验证声明中出现、该设备/系统版本不支持。
   这类问题不能由用户在设置里点一下恢复，详情页必须给出可诊断原因。
2. `已关闭`：本机能力开关为关闭。这是用户自己的决定，不是故障。
3. `需授权`：开关开启但存在一项可由用户操作恢复的阻塞——Android 系统权限未授予、
   无障碍服务未开启或已断连、通知使用权未授予、尚未选择提供者、运行服务未就绪。
4. `已开启`：开关开启且所有前置条件成立，即能力当前真的可以被调用。

**「已开启」与「已就绪」的统一定义：** 主页面显示 `已开启` 当且仅当详情页的
「运行状态」同时显示 `已就绪`。二者不是两套判据，而是同一判定的两个呈现层级：详情页把
判定拆成四条独立事实（能力开关、Android 系统权限、运行状态、Core 同步），主页面把它们
折叠成一个状态词。任何一条事实为否，主页面都不得显示 `已开启`。

Core 同步状态不参与上述四级判定，只在详情页单独显示。Core 断连不影响本机开关与本机授权的
查看和修改，也不得被显示成插件缺失。

## 四、内建能力的装配

### 4.1 装配方式

六项官方能力在构建 APK 时完整打包，安装后自然具备。启动时直接**从 APK 内置资源**完成校验、
注册和运行时加载，不再经过“安装到应用私有目录”的流程：

- 不写入插件安装根目录，不产生可被扫描的已安装插件记录；
- 不写启用状态标记，不出现“已安装但未启用”的中间态；
- 不需要用户执行任何安装、启用或初始化操作；
- 不依赖用户进入设置页面才完成初始化。

签名校验、清单形状校验、容器限制、ABI 校验与隔离边界完全保留：每个内建包在每次启动时
都要重新通过同一套 `AlpVerifier` 校验，校验失败不得注册、不得执行。

### 4.2 内建能力的可见性

- 不出现在插件管理中的任何列表里，不提供安装、启用、停用、卸载入口。
- 不允许普通用户单独停用插件运行时。是否允许 Agent 使用某项能力，只由该能力的详情页开关、
  授权策略和 Android 系统权限决定。
- 第三方插件继续沿用现有安装、启用、停用、卸载、版本更新确认与隔离机制。

### 4.3 升级与旧数据

- 内建能力随 APK 版本更新：因为不持久化已安装副本，升级后自然使用新 APK 内的版本，
  不会继续加载旧版本残留文件。
- 旧版本可能已在应用私有目录留下官方 ID 的安装副本。升级后这些副本**不参与加载**：
  磁盘扫描按“已成功加载的内建 ID”过滤，目录本身不删除、不移动，用户此前保存的插件数据
  仍留在原位置。
- 已保存的本机能力策略必须跨内建版本保留。既有策略键由插件 ID、作者指纹、能力 ID、
  Schema 摘要、风险等级与原语摘要组成，**不含版本号**，因此内建版本升级不会改变键，
  用户明确关闭的能力不会被重新打开。Schema 或原语本身变化时会生成新键，这属于能力语义
  变化，不做静默迁移。
- 插件安装/启用与能力授权仍然是两件事：内建能力“随应用就绪”不等于“能力被默认授权”。
  能力的默认策略保持既有语义：开关默认开启、授权模式默认「每次手动」、主动推送默认关闭。
  任何请求仍须按本机策略与系统权限单独裁决。

### 4.4 失败必须可诊断

内建能力加载或校验失败时，对应能力在主页面显示 `不可用`，详情页显示可诊断原因
（包缺失、签名无效、清单无效、ABI 不支持等稳定原因码），绝不显示为可用。
一个内建能力加载失败不影响其余五项。

## 五、能力详情的统一结构

每个详情页按同一层次组织，顺序固定：

1. **能力开关与授权模式**：总开关 + 每次手动 / 允许只读 / 自动允许，并保留该能力已有的
   专属设置（短信被动范围、通知采集范围等）。
2. **Android 系统权限**：逐项显示真实状态与正确的系统入口，文案说明“授权后能做什么、
   不授权会怎样”。
3. **运行状态**：真实可用性，不可用时说明缺什么、下一步做什么。
4. **Core 同步**：Android 能力状态是否已同步给 Core；Core 离线只影响这一行。
5. **该能力专属设置**：如前所述。

任何一条都不得用单一绿色「已启用」代替其他条件。系统权限、本机能力授权、运行时可用性与
Core 同步状态分别判断，避免互相矛盾的结果。

### 5.1 短信详情

- 主开关：「短信读取」（对应查询能力），附带被动范围设置（全部 / 关键词 / 电话号码、
  正文开关）。
- 三项子能力各有独立开关：「短信定时任务设置」「短信任务状态查询」「短信任务取消」。
  三项都只控制对应能力的实际调用权限，不连带扩大读取范围。
- Android 系统权限：短信读取权限，入口走系统权限申请；被永久拒绝时引导到应用权限设置。
- 短信主动推送：开关、范围、正文开关、推送目标多选。推送目标只列出已通过认证发现的
  稳定端点。
- 不包含加密队列容量、保留时长等底层配置。

### 5.2 通知读取详情

- 能力开关与授权模式。
- Android 系统权限：通知使用权，入口跳系统「通知使用权」设置页。
- 通知采集范围与投递：沿用既有内容（应用列表选择、正文开关等），行为不变。
- 通知主动推送：开关、应用范围、正文开关、推送目标多选。
- 不包含加密队列容量、保留时长等底层配置。

### 5.3 屏幕详情

屏幕读取、屏幕截图、屏幕控制是三项独立能力，授权互不扩大。

**屏幕截图**的系统权限判定改为截图来源优先：

- Android 11（API 30）及以上，默认优先使用无障碍服务截图。
- 无障碍服务可用时（设置中已开启、系统当前确实已绑定、服务声明了截图能力），显示为已就绪，
  系统权限入口跳转无障碍设置，不要求用户再做屏幕共享授权；此时界面不得弹出、也不得引导
  用户发起 MediaProjection 系统对话框。
- 无障碍服务开启过但当前未连接时，显示“服务已断连”，入口仍是无障碍设置，并说明需要确认
  服务显示已连接。
- 无障碍服务从未开启时，显示需授权，首选入口是无障碍设置，同时说明 MediaProjection 是
  需要明确同意的备用方案。
- 服务已连接但未声明截图能力，或系统版本低于 Android 11 时，如实显示不可用并说明原因；
  低于 Android 11 时以 MediaProjection 为可用路径。
- MediaProjection 只在无障碍路径不可用且用户明确同意时使用，任何情况下都不静默发起。

屏幕读取与屏幕控制各自独立显示无障碍服务状态与入口，不因截图能力就绪而显示为已授权。

**停止屏幕请求**保留在屏幕各详情页中：撤销全部临时授权并终止当前屏幕请求，长期设置与
系统权限不变。临时授权的逐项撤销随能力走：详情页只列出**这一项能力**真正生效的批准，
支持逐条撤销与全部撤销，不再在主页面单列一张混合清单。

### 5.4 通话记录详情

能力开关与授权模式、通话记录读取权限、运行状态、Core 同步。无专属配置。

## 六、主动推送的归位

- 主页面不再有「短信与通知主动推送」独立入口，`短信与通知主动推送` 路由不再作为用户可达页面。
- 通知主动推送的配置移入「通知读取」详情，短信主动推送的配置移入「短信」详情，两处各自
  显示自己的推送目标。
- 两处配置仍写入同一份安装实例级推送配置，语义与既有实现一致：被动范围与主动推送独立，
  主动推送默认关闭，推送只到用户选中的可验证端点。
- 加密离线队列的容量、保留时长与队列统计不再作为设置项展示；底层队列、已保存的配置值、
  到期与撤销清理逻辑全部保留，继续按既有默认值（72 小时、1000 条、4 MiB）与用户已保存值
  运行。移除的是配置入口，不是能力。

## 七、应用名称显示

通知范围选择保存后，再次打开详情时会先显示「应用信息暂不可用，已保留原有选择」，稍后
才变成真实应用名。这是把“尚未读完应用列表”误当成“应用不可用”。

修复要求：

- 已保存选择的应用名称来自进程内缓存的已安装应用目录，再次打开时立即显示名称与图标。
- 缓存刷新时保留旧值，只有在真正读不到时才降级，且降级文案不得声称“应用信息不可用”。
- 读取中显示的文案只表达“正在读取”，不得与“已保留原有选择”混用。
- 已选但当前不可见的应用仍按既有行为保留并可取消；这条语义不因本次修复改变。

## 八、视觉与交互约束

- 复用现有 Material Design 3 组件与令牌：分组卡片、设置条目、图标底衬、语义状态色
  （成功 / 等待）、动态配色、深浅模式、圆角与间距令牌。
- 复用现有设置导航与进入、退出动画，遵循系统的减少动态设置。
- 手机全屏与平板侧栏两种承载方式都保持可用，跨断点保留同一份草稿与滚动位置。
- 不引入新的设计语言、色值、第三方 UI 框架。
- 状态刷新自然，不闪烁、不跳布局。状态变化只改文字与语义色，不重建整页。
- 文案简洁、面向用户，不出现插件 ID、能力 ID、状态码、Schema、原语等内部术语。

## 九、不变量（不得破坏）

| 不变量 | 来源 |
| --- | --- |
| Android 安装实例是设备能力授权的唯一权威，切 Core、账号、Agent、断网、重启不重置策略 | ADR-0059 |
| 插件安装/启用、能力开关、系统权限、数据范围、系统强制同意互相独立 | ADR-0059、GLOBAL-01/03 |
| 已明确的本地关闭不得被升级、迁移或默认值打开 | GLOBAL-02、AUTH-03 |
| 未认证、未配对、跨账号、错误签名、过期请求继续拒绝 | AUTH-06 |
| 屏幕读取 / 截图 / 控制保持独立授权，任何一项不得扩大其他两项 | GLOBAL-10、ADR-0059 |
| MediaProjection 仍须用户经前台 Activity 明确同意，票据与策略、宿主版本、停止代次绑定 | 既有屏幕规格 |
| 临时授权按能力、操作、已批准数据范围共享；撤销、取消、到期、重启安全 | GLOBAL-05 |
| 主动推送默认关闭，只到已验证端点；被动范围与推送范围独立 | GLOBAL-06/07 |
| 状态必须指出真实阻塞项，不得硬编码就绪、不得隐藏错误 | AUTH-09 |
| 界面不得硬编码颜色与越界圆角，必须走主题角色与圆角令牌 | 既有视觉令牌守卫 |

## 十、非目标

1. 不重构 OAI Core、Gateway 或 Agent 通信协议。
2. 不修改设备能力 API 与插件调用契约、插件包格式、WASM 运行时与 ABI。
3. 不重写已经正常工作的截图底层实现（无障碍优先、投屏备用的编排逻辑保持）。
4. 不重新设计整个 App 设置系统，不新增设置入口。
5. 不删除短信定时任务、主动推送、临时授权等真实业务能力。
6. 不大规模重构第三方插件系统。
7. 不修改无关模块。

## 十一、验收

- 全新安装后不进入任何设置页面，六项官方能力即可被 Agent 调用（受本机策略与系统权限约束）。
- 插件管理中看不到六项官方能力，也没有任何安装或卸载它们的入口；第三方插件管理不受影响。
- 应用升级后内建能力使用新版，已保存的开关与授权模式不被改变；旧安装副本不再被加载。
- 主页面结构为三组六项加插件管理，无临时授权区、无独立主动推送入口、无插件 ID 与技术说明。
- 每项能力状态与详情页的四条事实一致，主页面 `已开启` 当且仅当详情页 `已就绪`。
- Core 离线时详情页仍可查看和修改本机开关与授权模式。
- 无障碍可用时截图详情页不要求屏幕共享授权；无障碍不可用时显示正确原因与无障碍设置入口。
- 通知与短信的主动推送配置分别位于对应详情，各自显示推送目标；不存在独立推送页面与队列配置项。
- 通知范围再次打开时立即显示应用名称，不出现「应用信息暂不可用」。
- 深浅模式、动态配色、平板侧栏、减少动态下的页面与转场保持一致。

## 十二、测试接缝

实现采用三层接缝，优先复用既有接缝，避免新造抽象：

1. **纯函数层（首选）**：能力目录与状态聚合是纯数据变换，可在 JVM 上直接断言分组、行数、
   状态词与判定顺序；截图系统权限展示由截图诊断的分类结果映射而来，同样只依赖既有枚举。
   既有先例：能力目录与临时授权测试、权限映射测试、能力阻塞分类测试。
2. **装配用例层**：内建能力加载是一个注入式用例（资源读取器、校验器、注册器的接口边界），
   可断言首次加载、重复启动幂等、校验失败不注册、一个失败不影响其他项、旧安装副本退出加载、
   策略跨版本保留，且断言它从不写入插件安装根目录。
3. **页面层**：沿用既有 Robolectric + Compose 测试，经设置外壳进入页面，断言分组与条目、
   状态词、详情页四条事实、入口跳转、无插件 ID 与无技术说明。

测试只断言外部可见行为：用户看到什么、点了之后发生什么、系统收到了什么权限请求；
不断言私有实现细节。
