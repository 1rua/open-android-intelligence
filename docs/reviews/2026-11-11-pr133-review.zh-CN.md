## 发现 1：跨 Agent 同名会话误抑制完成通知（P2）

变更入口：`apps/android/app/src/main/kotlin/com/openandroidintelligence/mobile/GatewayRuntime.kt:2547`。

新回调将主工作台的原生事件送入通知层，但既有消费端没有完整匹配 Agent 身份：

- `GatewayRuntime.kt:220` 将通知目标缩减为 `conversationId` 后调用前台抑制判断。
- `GatewayRuntime.kt:421-426` 只比较助手工作区的会话 ID，没有核对该工作区所属 Agent。
- `ReplyNotifications.kt:179-181` 命中抑制时撤回目标通知并返回。
- `ReplyNotifications.kt:362-366` 已在发布之前持久消费该轮完成事实，离开错误命中的助手界面后不会补发这一轮完成提醒。

复现：DSH 主工作台在 `native-session` 发起任务，切换到 Codex，再让系统助理显示 Codex 自己的 `native-session`。此时释放 DSH 的受控任务。DSH 的通知会话正确变成 `COMPLETED`，最终正文也正确，但会因为 Codex 的同名会话可见而被错误抑制。

定向验证结果：助手可见时系统回复通知数为 0；助手不可见的对照流程通知数为 1。检查通知前取得通知协调器的同一把锁，等待完整事件处理结束，并确认 `done.*` 完成围栏已经存在，排除抢在通知发布前断言的误差。

这违反 issue #132 的“符合既有前台策略”“通知及点击入口准确关联会话”要求。原生会话 ID 只在 Agent 内唯一，已有 `NativeNotificationRoutingTest.kt:14-17` 明确记录此约束。

建议：前台抑制接收完整通知目标，并同时匹配助手工作区的 Agent 和会话身份。保留查看同一 Agent、同一会话时的原有抑制策略。

## 发现 2：另一 Agent 的运行记录阻止当前会话归档、删除（P2）

变更入口：`apps/android/app/src/main/kotlin/com/openandroidintelligence/mobile/GatewayRuntime.kt:2547`。

新回调让主工作台的运行状态首次进入共享通知集合；`GatewayRuntime.kt:2859-2863` 随后把所有 Agent 的运行记录仅按 `conversationId` 放进当前控制器的外部忙碌集合，丢失了 Agent 身份。`conversation-ui` 模块的 `WorkbenchController.kt:1288` 直接用这个集合阻止归档、删除操作。

复现：DSH 的 `native-session` 仍在流式回复时切换到 Codex，打开 Codex 自己的 `native-session` 并尝试归档。Codex 控制器自身 `hasActiveWork=false`，通知集合中也只有 DSH 的运行记录，但归档立即返回：

```text
CONVERSATION_BUSY:请等待当前发送和回复结束
```

归档在上述忙碌检查处即被拒绝；删除使用同一入口，静态调用链确认同样受影响。

已排除“切换 Agent 会清除旧任务”的反例：`GatewayRuntime.kt:2955` 只关闭旧工作台控制器；仓库按 Agent 缓存，发送任务由 `CoreAgentConversationRepository.kt:1229` 的 `parentScope.launch` 持有，旧任务仍继续，通知记录也不会因为切换 Agent 而清空。

这违反根 `AGENTS.md` 的“保留已有能力”要求，并构成通知接线带来的会话管理回退。建议将通知运行记录按当前控制器固定的 `ownerAgentId` 过滤后，再提取会话 ID；保留同一 Agent 会话在途时的管理保护。
