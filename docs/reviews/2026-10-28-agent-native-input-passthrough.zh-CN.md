# Agent 原生输入透传与发送模式选择修复

日期：2026-10-28

基线：`dev@1e51df0850d5a0bc00d37273f21610ec5a7eeb5f`

## 用户要求

网关与客户端负责把原文交给宿主，不额外裁剪 Agent 工具或替宿主决定忙碌输入策略。
Agent 尚未回复时，“引导 / 排队”只选择发送模式；点击发送键才提交。引导选项不能
因缓存能力位缺失、为 false 或尚未收到首个轮次标识而不可选择。

## 复现与根因

### 发送模式和客户端预判

原 Composer 在生成中禁用发送键，两个模式按钮直接调用提交回调。点击“排队”即会
发起提交并清空草稿；引导按钮同时受能力位、附件和生成状态限制。新增回归在原实现
中出现 `23 tests completed, 5 failed`，覆盖点击只选择、QUEUED 状态、能力位为 false、
模式变化后的请求身份和已选择引导不能被改成普通发送。

Android Repository 和 Gateway Client 还会在真实请求发出前判断能力位和本地轮次。
Core 与远程适配器继续按缓存 `steer` 能力拒绝。Core 回归证实宿主有实际接口时仍得到
`UNSUPPORTED_CAPABILITY:405`；客户端未传轮次标识则得到 `INVALID_REQUEST:400`。

### 插件绕过了 Hermes 的原生忙碌处理

原 `steer_native_turn()` 直接调用宿主 `_steer_running_agent()`，最终使用
`agent.steer()`。真实固定 SDK 中，该接口等当前工具批次完成后再消费输入；原生 busy
dispatcher 在 interrupt 模式下使用 `agent.redirect()`，能够中断当前模型请求并注入输入。

使用真实 SDK 的 dispatcher 和 `InterruptControlMixin`，只控制模型状态、不启动模型或
执行命令。将旧两个引导方法放回后，回归明确因没有进入宿主 interrupt 路径而失败；
恢复修复实现后通过。

原生消息入口还只允许 `/approve`、`/deny` 绕过 generation 锁，其他宿主命令会被插件
延迟；`/new` 在普通消息路径中也有沿用旧命令端点的直接返回。现在原生命令统一交给
宿主解析，旧命令端点已创建会话的防重复处理只保留在该旧端点。

### 工具集合核查

没有根据截图中模型自述认定插件屏蔽了终端。已用固定 SDK 验证 canonical 与两个
legacy 平台的真实工具解析：

| 宿主配置 | 结果 |
| --- | --- |
| 默认配置 | 包含 terminal 等宿主核心工具 |
| 只配置 CLI 平台为 file | 不影响本接入平台的默认工具 |
| 宿主显式配置本平台仅 file | 按宿主设置不加载 terminal |
| 宿主全局禁用 terminal | 按宿主设置禁用 |

适配器 `toolsets_for_source()` 保持 `None`，不维护额外工具白名单，也不覆盖宿主明确
设置。以上是源码与隔离 SDK 证据，不证明截图当时的模型实际获得了哪些工具；仍需
同窗运行日志才能归因终端不可用。

## 最终行为

- 主会话、浮动面板、气泡会话共用模式选择：生成中默认引导，点击模式只改变选择，
  保留草稿；点击发送键才执行选中方式。原有回车换行习惯保持。
- 引导原文送到宿主，宿主拥有真正的 interrupt、steer、命令解析和自身忙碌策略。
  网关不把输入擅自改成本机排队；显式选择排队才进入本机队列。
- 客户端不按命令前缀对 `/approve`、`/deny` 特殊分流，其他原生命令同样可原文发送。
  宿主直接回复保留原消息标识，经原生消息流回到客户端。
- 未收到宿主轮次标识时可以提交；服务端按已认证账号和指定会话读取当前轮次。
  已提供标识时仍严格核对；重复请求使用首次回执，不会改投后继轮次。
- 明确失败后用户改选模式，会创建新的请求身份；结果未知时，控制器也禁止跨模式
  再提交，须先查询。失败不会清空草稿、悄悄改选排队或伪造成功。
- 引导请求使用原 `clientMessageId` 作为签名请求和幂等标识；回执丢失按结果未知处理，
  同一请求重试保持原身份。迟到回执不会覆盖已经开始的新轮次的控制标识。
- 确定未转交的 `STEER_UNAVAILABLE` 保存明确错误回执，同键重放不会变成结果未知。
  用户再次显式发送这类失败引导时建立新身份；未知或其他失败不会套用此规则。
- 接收回执表示“已交给宿主”，不表示模型已执行完成；无法到达真实处理器时返回错误。
- 忙碌时的 `/stop` 等命令不等待其 drain 出来的后继任务；后继回复不进入本次命令回执。
- 当前引导载荷为文本。携附件时选择项仍可选，无法提交会保留草稿和附件，不会丢掉
  附件仅发正文。附件上传与普通发送继续沿用既有路径。

账号鉴权、服务器已登记 Agent、原生会话归属、轮次/活动任务关联与幂等继续保留，
这些检查保护操作对象，不参与选择 Agent 的工具集合。审批卡 UI 沿用此前确认的版本。
没有修改账号、密钥、配对、原生会话或历史数据库格式。
