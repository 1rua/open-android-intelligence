# setup 安装 Hermes 与 DSH 插件失败修复

日期：2026-11-06。开发基线：`473d2c0b17c4e67517d68b80feee190f930bcd97`。工作分支：`feature/fix-setup-plugin-install`。

## 已确认的问题

用户报告 setup 安装两个宿主插件均失败。本次基于源码及隔离测试确认以下安装缺口，未将其等同于尚未提供日志的用户部署现场。

- `configuration._configure_agents()` 发现候选后直接进行真实注册握手，只有 DSH 返回 `AGENT_BRIDGE_UPGRADE_REQUIRED`（404）才提供升级。尚未安装插件导致桥接端不可用时，两个宿主均直接返回，未执行安装。
- Hermes 的候选准备仅同步 Python 模块及环境文件，不安装和启用标准插件入口。未被主流程调用的 `scripts_runtime._install_agents()` 使用 `hermes plugins install ./integrations/hermes-session-adapter`；固定 Hermes SDK `75b083e9399115b12513385252811f09c3503c90` 的 `_resolve_git_url()` 将该参数解析为远端仓库简称，不能作为本地目录安装。
- DSH 的 Python 发现、安装前检查及 Node 安装辅助器只接受已经启用旧/新会话 bundle 的 profile，无法向现有普通 profile 首次安装适配器。

## 修复边界

管理员先选择并确认 Agent 候选。仅对能够匹配本机宿主配置的不可用或旧版会话桥提供安装，认证失败和无效握手响应不触发安装。

- Hermes 使用其宿主 Python 环境安装当前仓库的 Core 和会话适配器，通过标准插件发现和启用流程完成接入准备。安装须再次确认，并保留旧插件及配置备份。
- DSH 在桥接端不可用时允许列出尚未安装会话 bundle 的现有有效 profile。管理员明确选择一个目标，安装器通过备份中绑定的显式标记接受首次安装，继续使用官方管理 API、写锁、兼容性检查及失败恢复。旧桥在线升级继续采用原有筛选规则。
- 安装后再次调用真实 HTTP 握手。宿主尚未重新加载时保持未注册，提示重新加载后重试。正常在线的插件不重复安装。
- 本次不创建或合并宿主账号、不替换主密钥、不修改平台或原生会话身份及历史。远端或不匹配的自定义候选不会修改本机插件。

## Hermes 安装与恢复的界限

安装器分别核对当前 Core 实例的管理权限和宿主路径，在每次子进程启动及文件写入前重新检查授权。解释器通过原虚拟环境路径启动，支持标准解释器链接；模块和配置目录不接受任意链接。环境中的其他管理令牌不传给包管理器或 Hermes 子进程。

配置及插件入口保存在所选 Hermes 主目录的 `.oai-hermes-install-*` 下。官方启停命令失败后不重写活动配置；若配置已经变化，保留当前文件、插件和恢复材料，并要求人工核对。配置仍与原文件一致时才恢复插件入口，避免把并发改动误当作安装器自己的写入。Python 包管理器对 site-packages 的部分更新不属于配置回滚范围，错误后需使用保留的材料检查并重试。

当前自动安装使用本用户的标准 `hermes-agent/venv`；跨用户宿主返回明确错误，不将 root 的管理身份静默转换为另一用户。root 操作其他用户 Hermes 的自动安装路径尚未实现。

Hermes 安装辅助器最终聚焦回归 **22 项通过**，其中标准插件目录通过固定 SDK 的真实 disable/enable CLI 验证；新增并发修改用例先失败后修复。包管理器执行通过隔离进程替身验证，不代表已安装到真实宿主。

当前文件系统即使在允许的原生命令环境中也不能创建链接（`ENOENT`）。实际 venv 与可执行文件链接用例已加入自动化测试，仅在该文件系统能力缺失时跳过，由 CI 原生 Linux 环境继续执行；不将链接分支模拟验证表述为本地真实链接验收。

## PR #90 的 CI 跟进

提交 `00421c7dd060072baff33b2cf8514739880f2fb1` 对应 CI `42226612823` 中，Core 的 Python 3.11、3.12 各有两项失败：`test_real_standard_venv_and_executable_links`、`test_uninstall_uses_the_installations_python_for_authentication`。同次 Hermes、DSH、Android 和 APK 检查均通过。

两项失败来自测试构造对共享解释器元数据的假设。真实 venv 测试直接链接 GitHub 托管的共享 Python，目标被 `_safe()` 拒绝；日志未打印具体权限或链接数，因此不将共享解释器的某一权限值当作已知事实。卸载测试使用 `copy2` 覆盖私有 stub，继承源解释器权限，导致模拟的“私有安装解释器”不满足权限要求。用 worktree 内的副本分别设置 `0755`、`0775` 后复现旧测试为 1 项失败、1 项通过，`0775` 返回与 CI 相同的安全拒绝信息。

本次仅修正测试：真实链接用例先创建普通复制的 venv，将受控私有解释器设为 `0700` 后再建立真实链接，保留 `sys.prefix` 的实际子进程检查；卸载用例显式收紧私有副本权限，并同时覆盖两种源权限、确认源文件权限未变。另补三种组或其他用户可写的解释器仍须被拒绝的回归。安装器和卸载器的生产安全校验未修改，未更改共享 Python 权限。

聚焦验证：卸载回归在 Python 3.11.15 上 **62 项通过**；Hermes 安装回归 **25 项通过、1 项跳过**。真实符号链接测试仍受当前文件系统能力限制，留给更新后的 CI 执行；本地跳过不计为真实链接验证通过。
