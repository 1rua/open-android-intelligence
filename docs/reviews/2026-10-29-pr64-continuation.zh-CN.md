## 原有 CI 失败的实际原因

起点提交的 [Actions 40791161514](https://github.com/1rua/open-android-intelligence/actions/runs/40791161514) 中，Core Python 3.11/3.12、Hermes native、DSH 均通过。Android 的设备与会话模块通过，App 单测编译在 `AuthSessionLifecycleTest.kt:123` 失败，报 `Unresolved reference 'awaitCondition'`；后续 Play 检查跳过。这不是 App 单测通过。

该测试还使用了已经失效的认证路径和响应结构。本轮同步当前 dev 中该测试的修复：使用真实协议路径、完整协商响应、明确的有界异步等待和离线退出断言。该同步只修改测试夹具，不更改认证业务代码。

本地首次验证与另一次 Gradle 构建重叠，导致 APK 测试中间文件缺失。记录为验证环境竞态，随后统一串行运行；不能把这次失败解释为业务缺陷，也不能将其计为通过。

## 断线提示的生成方与证据边界

已核对 Hermes SDK `75b083e9399115b12513385252811f09c3503c90` 的源码；测试使用的干净 SDK 副本与该提交的下列文件逐字节一致。

| 可见文字 | 原生生成方 | 源码表达的触发边界 |
| --- | --- | --- |
| `Recovered reply` | `gateway/delivery_ledger.py` 的 `RECOVERED_MARKER` / `RECONNECTED_MARKER` | 宿主启动恢复或平台投递失败后的 ledger 重试；不等价于手机观察连接断开 |
| `System note: The previous turn was interrupted...` | `gateway/run.py::build_resume_recovery_note`，由 `gateway/run_turn_runner.py` 的 `resume_pending` 分支调用 | 宿主认为上一轮被中断，自动恢复或新消息到达时构造恢复输入 |

`_prepare_resume_pending_message` 对真实新用户文本保留原始文本；空的自动恢复输入则会把 note 持久化为 user 行。这是上游宿主行为。仅凭 role=user 且缺来源信息的历史记录，适配层不能安全区分内部 note 和用户主动发送的相同文字。本轮不按正文匹配删除、改写角色或伪造用户身份。

手机断开只应结束观察读取。隔离测试需要证明已受理执行仍只分派一次、继续完成并留下可按原 ID 查询的持久终态。宿主进程真正停止后的恢复由宿主能力决定，不能用“当前没有活动任务”推导成功。
