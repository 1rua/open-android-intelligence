## 可定位问题

### P2：首次发送结果未知时，唯一用户原件仍受上传暂存 TTL 清理

位置：`WorkbenchController.kt` 的 `submitWhenAttachmentsVerified`，审查时第 1780–1800、1835 行；`GatewayRuntime.kt` 第 164–169、1204–1212 行；`EncryptedAttachmentStagingStore.kt` 第 111–113、443–459 行。

- 生产调用顺序为发送事实落盘、网络 `submitMessage`、受理后 `releaseSubmittedAttachment` 内归档原件。首次网络请求超时或在回执前杀进程时，受理后的归档语句没有执行。
- 当前这次未知结果的处理只保留发送身份、正文和远端附件 ID。正常发送路径没有在网络提交前启动并等待原件归档，后续冷启动才尝试根据已保存消息恢复媒体。
- 上传暂存仍在构造时按 24 小时清理，Runtime 冷启动还异步调用全范围 `cleanupExpiredRoot`。因此“发送超时、关闭 App 超过 24 小时、再启动”可先清理唯一字节，随后本地恢复无法把原件归档。服务器原件已经消失时，记录仍在但原件不可恢复。

该问题违反规格“发送结果未知时保留原件与发送身份”。这是源码调用链确认的生产问题；本审查未运行计时故障复现。

修复方向：在网络提交前等待已校验用户原件归档；未知结果仍有发送重试义务的暂存不得被普通 TTL 清理，或必须能从持久原件重新建立暂存。补充首次发送无回执、重启前跨越 TTL 的回归，验证原件可读且重试查询沿用原身份。

主 Agent 已认可此问题，并交由会话实现 Agent 修复。修复状态须在后续不可变提交复核时更新。

### P2：一条失败下载恢复日志阻塞账号的全部新下载

位置：`AndroidAttachmentDownloads.kt` 第 47–54、120–157 行；`GatewayRuntime.kt` 第 1002–1006 行。

- 每次 `download` 在 `recovered == false` 时先调用 `recoverLocked`。恢复中任一旧日志失败，方法最终抛出 `DOWNLOAD_RECOVERY_FAILED`，`recovered` 继续为 `false`，新下载尚未创建就退出。
- Runtime 会捕获同一恢复失败，使登录继续；但既有恢复入口没有撤销这条日志。新下载因此仍在每次点击时重复处理同一不可恢复日志。
- 可达场景为进程中断留下 pending 文件和日志，之后原消息删除或原件不可用。该旧导出记录无法重新读取原件，其他完好的附件也无法下载；界面没有独立取消旧意图的入口。

该问题违反“恢复失败保留日志且不阻止正常使用”的行为，影响整个账号的下载能力。这是源码控制流确认的生产问题；本审查未运行 MediaStore 故障复现。

修复方向：逐条隔离恢复结果，永久失效意图应取消并安全回收，暂时失败保留可重试记录；旧记录恢复失败不能挡住独立的新下载。增加“旧日志失败、另一附件的新下载成功”的回归，并核对 pending 文件不被错误发布。

主 Agent 已认可此问题，并安排媒体实现 Agent 修复。修复状态须在后续不可变提交复核时更新。
