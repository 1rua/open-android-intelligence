## 已确认根因

### 1. SDK 缺失时，测试自身的失败注入未被触发

`tools/test_smart_test.py::test_adapter_only_edits_execute_native_suite_and_propagate_failure` 只在命令包含 `test_native_tool_events.py` 时注入退出码 7，但这个文件只在找到固定 SDK 时才进入命令。

本地存在 SDK，因此原测试通过；独立 Core CI 没有 SDK，注入条件不成立，实际返回 0。问题在测试的环境前提，不应强迫独立 Core 安装 Hermes。

修复：分别模拟 SDK 可用与缺失，检查两种情况下的失败传播，并检查三个 SDK 专属文件仅在 SDK 可用时被选中。模拟会屏蔽本机固定 SDK 目录，不依赖机器是否预装 SDK。

### 2. root 权限用例的模拟所有权不完整

`oai-core/tests/test_hermes_installation.py::test_root_user_can_install_adapter_for_foreign_owned_host` 把进程模拟为 root、把 Hermes 目录用户固定为 1000，却让 Core 源目录保留运行机器的实际所有者。

CI 中 Core 源目录因此不满足安装器原有的“root 或目标用户拥有”要求，正确触发 `HERMES_PATH_UNSAFE`。本地把目标用户改为 1001 即可复现相同拒绝路径。1001 是回归样本，不将其当作日志已输出的 CI 实际用户编号。

修复：参数化用户/组 1000 与 1001；完整模拟 root 所有的 Core 与目标用户所有的 Hermes 目录。`stat`、`lstat`、打开文件后的 `fstat` 按文件标识保持一致，文件类型、权限位和链接计数仍来自真实文件。保留完整安装链与目录生成断言，并加强用户/组转交断言，不放宽生产安全规则。

### 3. 后台复查未真正运行，却记录完成

旧监控脚本尝试恢复仍由当前客户端占用的同一线程，日志明确报告 `thread-store conflict: already has an active writer`。脚本忽略了子进程非零退出码，仍输出“完成”。

改进方向：创建独立只读复查任务，持久化每个 SHA 的检查结果、错误和回调退出码，失败检查出现后尽早触发，禁止把回调失败写成成功。实际源码修复由本线程持续目标负责，后台复查不自行合并或越过审批提交。
