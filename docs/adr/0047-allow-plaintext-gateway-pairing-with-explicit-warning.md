# 允许使用明文 HTTP 完成 Gateway 配对，并如实标注未加密连接

用户显式输入的 `http://` Gateway 地址现在可以完成配对、登录、会话恢复与事件流：传输层按 http/https 两种 scheme 打开连接，配对不再强制要求 HTTPS。默认链路仍是直接 HTTPS + SPKI 指纹核验，且 HTTPS 连接必须在协商返回可用 `tlsSpkiSha256` 时完成指纹固定，缺身份即失败，因此"允许明文"没有放宽 TLS 路径的任何要求。

明文降级受硬约束，而不是少做一次检查：声明了指纹的 profile 不允许构造在明文地址上，连接分类也会在握手之后、写入请求体与信任响应之前以 `PIN_REQUIRES_HTTPS` 拒绝明文连接，所以已固定身份的账号无法被任何可到达的服务端诱导降级。地址 scheme 不受支持时（例如 `ftp://`）在发起任何网络请求前即以 `AUTH_INVALID:url-scheme-required` 拒绝，不做静默升级、改写或猜测。

未加密是可见状态而不是默认值：登录表单在地址为明文时持续显示未加密警告，连接成功后登录页与设置页按真实等级标注「未加密（HTTP）」，不再对明文连接显示「TLS 已固定」。这修正了 2026-09-03 真机报告 D-004 中"界面静态显示 TLS Pinned"的失真部分；该条目原先要求的"默认只允许 HTTPS"由本 ADR 明确取代，其余要求（持续警告、身份如实呈现、不把明文当作已核验身份）继续有效。

代价：局域网明文配对会把账号口令、消息与附件内容暴露给同网段的旁观者，这是用户选择明文地址时接受的取舍，App 用持续警告与状态标注把它显式化而不是掩盖。Android 侧需要 `usesCleartextTraffic="true"`，平台层不再代替产品拦截明文，该风险因此完全由用户的显式选择与警告承担。
