# 消息合并由 Android 客户端独占，不再按 Core 配置

> **2026-11-13 目标范围**：客户端独占消息合并、默认零延迟等用户行为保留；旧 POST message-batches 及 Gateway 编码不保留，按 Remote 实际能力适配。 见[新总规格](../specs/2026-11-13-dsh-remote-architecture-refactor.md)。本次仅确认目标，不宣称运行时代码已变更。

ADR-0045 把「普通文本防抖」定义成可按 Gateway 覆盖的全局策略，默认 1.5 秒、范围 0–10 秒，
并且后续消息默认延长窗口。这个定义带来两个问题：设置界面出现「覆盖当前 Core 的设置」，
让人以为这是 Core 的服务端配置；默认 1.5 秒又让「点发送立刻发出」不再是默认体验。

本 ADR 明确四条边界。

**一、合并只发生在手机上。** Android 客户端在本地暂存待发送的普通文本，窗口结束时以一次
`POST …/message-batches` 提交；Core 只接收客户端最终提交的消息。客户端不读、不写任何
Core 合并配置，设置页没有「按 Core 覆盖」的入口。

**二、默认不合并。** 偏好键 `global:delay` 缺失时按 0 秒处理，即点击即提交，不进入合并队列
（仍以普通待发送行显示，受理或失败后移除）。只有用户主动选择大于零的时长才会合并；范围 0～30 秒，每秒一档。

**三、容量上限保留，取消「延长等待」开关。** 单批最多 20 条、总字节不超过协议批次上限
（64 KiB）、从首条起最长 30 秒；窗口不再区分固定 / 延长两种模式，后续消息总是顺延窗口，
但不会超过上述硬上限。

**四、不迁移旧的按 Core 键与旧备份的合并值。** 旧版本遗留的 `gateway:<sha256>:delay` 键不再读取，
也不会变成客户端配置，避免升级后意外开启合并。旧备份文件里的 `global` 值同样不继承：
旧版导出会无条件写入读取时的默认值 1.5 秒，文件里无法区分「用户主动设置」和「从未设置」，
继承它就会让「升级后默认 0 秒」失效。旧备份的合并节因此整节跳过，并在导入结果里如实说明。

ADR-0045 中其余约束（独立 `clientMessageId`、`newline-v1` 聚合、斜杠命令与附件是硬边界、
同一线程单生成、幂等重试、重启后未获终态须由用户确认）继续有效，不受本决定影响。
